# Real mined-drop pickup via frozen learned Minecraft components

**Verified in actual Minecraft Java 1.21.3, Fabric/MCio, November 2–3 2026.**
This is the project's first repeated audit where **TWO previously trained
components** mined a real survival oak log and then moved to collect the
ordinary dropped item into actual inventory. It is NOT a from-scratch
*joint* end-to-end policy, a learned tree detector, navigation from spawn,
or an Any% speedrun. The experiment controller prepares and pre-aims a
log ONLY before each scored phase; a transparent event-based supervisor
switches to pickup actions once actual vanilla `minecraft:mined` increases.
The two frozen policies never receive world seed, privileged target XYZ,
controller commands, planned walking route or an admin item spawn.

## Inputs and frozen checkpoints

1. **Attack motor:** new from-scratch 6-feature player-own memory actor
   `mining_attack_motor_v1_own_crack_stage_interval6`: crosshair-hit
   boolean/distance, own crack animation stage/active, previous attack
   and elapsed ticks. Makes regular 6-tick LEFT_BUTTON hold/release choices.
   Trained previously in real game. Local ignored checkpoint
   `checkpoints/mcio_attack_motor_motorlearn_nov03a.pt` SHA256
   `4fe85be220306424f06e93ef7f8b0e76c6fbf4bd662da511ce028201be9bb6b8`.
2. **Drop pickup:** separate scratch-trained `PickupPolicy` from the
   project's earlier controlled pickup experiments. Its small movement
   model reads **only currently rendered RGB** through
   `pickup_features(frame)`, then picks one ordinary vanilla W/A/S/D key.
   The primary frozen `p02` checkpoint is
   `checkpoints/drop_pickup_policy_p02.npz` SHA256
   `163c2c427f24d776ca1f759ebb80d6363668107803a193f3fcf87ef9c966cf44`.
   The comparator `p01` checkpoint is also local and preserved.
3. **Environment:** new uniquely tagged disposable copied `DemoWorld`
   for each audit, `renderDistance=4`, VSync off, maxFps260,
   actual NVIDIA 320x180 rendered RGB and Java **SYNC** action packets.
   Only this player's fresh `GMAINCRAFT_MINING_FEEDBACK_V1` is requested
   with `GMAINCRAFT_MINING_FEEDBACK_ON_DEMAND_V1=1`, on the last tick
   of each six-tick attack action. No surface/chunk/dropped-item oracle.
   Prior game options are restored byte-for-byte and previous checkpoints,
   original personal Minecraft worlds and host Gentoo remain untouched.

**Crucial phase honesty:** The scoring supervisor can read Minecraft's
actual mined-block counter and inventory. It uses that event to start the
**pickup** policy, rather than letting a neural model independently decide
when to switch skills. During scored actions there is NO `/give`,
`/summon`, `/setblock`, `/tp`, `kill` or other admin command; each dropped
log was a legitimate physical item generated by ordinary player mining.
The controller may reset world, kill old drops, clear inventory, place a
three-block oak trunk and teleport the player to a slight aiming jitter
**between** episodes ONLY. Scored movement and attack use the same safe
`MCioAgentBridge`/`AgentAction` as normal survival gameplay.

## The cumulative stats bug was caught and corrected

The first `composed_pilot_nov03a` yielded real 5/5 mined logs and 5/5
inventory pickups with `p02`, plus always-forward 5/5. **However**, its
per-episode `mined_stat_delta` and `pickup_stat_delta` were INVALID:
MCio only sends changed *cumulative* stats; after each bridge reset the
first event was recorded as an episode delta 1, 2, 3, ... . The reliable
inventory scores in that pilot were unaffected because `natural_log_count`
reads actual current inventory, but pilot *event delta telemetry must NOT
be used as training rewards or event counts*.

`experiments/mcio_composed_log_pickup_probe.py` now holds the project's
existing `CumulativeMinedTracker` for oak-mined and pickup counters across
**all episodes and modes in one Minecraft world session**. Each new bridge
begins an episode with the tracker preserving the previous absolute
counter. It observes each six-tick vanilla mine action and each five-tick
pickup action. It asserts exactly one newly mined event when mined and
at most one new pickup event per scored case, rather than counting a
cumulative 20th event as 20 freshly mined blocks. In the corrected runs,
**every** positive inventory pickup has a **one-event pickup delta**,
and all no-movement/no-attack controls are zero. Real block mining and
inventory are verified separately, not inferred from synthetic rewards.

## Current synchronous on-demand mining sensor protocol

Previously the opt-in Minecraft crack-stage option was emitted on EVERY
game tick. In a single no-Torch fixed-scene control, 300 warmed ticks
needed 0.7440s with only status and 0.8109s with per-tick crack feedback.
To avoid unnecessary records, the new Java/Fabric version adds the independent
normal-action CBOR `MiningFeedbackRequest(fresh=True)` and Minecraft env flag
`GMAINCRAFT_MINING_FEEDBACK_ON_DEMAND_V1=1`. The observation handler
always clears the request after producing one observation: unrequested
packets **do not replay stale block-breaking state**. An `AgentAction` can
request current feedback on its very last six-tick game action, while
still separately requesting surface objects if needed. A new packet
changes scheduling only, NOT any mining gameplay actions or model features.

The relevant same-encoder, independently frozen evaluation
`motorondemand_eval_nov03a` re-ran 12 held-out pre-aimed cases using the
EXACT original trained motor checkpoint: **12/12** learned mined; 12/12
always-attack mined; 0/12 untrained, random or no-attack mined. Therefore
requesting the fresh stage once per decision preserved observed attack
competence. The script would raise when expected on-demand feedback was
missing, rather than silently accept an earlier sample. The no-Torch
benchmark `mineperf_demand_nov03a` returned **exactly 50** fresh feedback
options in 300 game ticks and none on the other 250, with zero frame gaps.
Its second/warm repeat took 0.7977s, versus prior continuous 0.8109s in a
separate launch; this does NOT establish a statistically significant
performance benefit by itself. See subsequent same-build controls if added.

Current opt-in Fabric JAR installed ONLY in disposable MCio DemoInstance
SHA256 `28fd3209bd15c9fecd1c2cdb3828b8dca3c17ff0840ea97e57be1f6da0cc05e6`.
Previous mining-feedback v1 JAR `7c41137b8789b0661700a322a90e4e7891752711b27786ac3fb5f750529d82c2`
was preserved in ignored `mcio-data/mod_backups/`. All older variants

## Next development gate

This is a working modular *attack-then-pickup* behavior only after the
controller has spawned the real oak trunk and aimed the player at it.
The phase handoff is still determined by the evaluator, so the agent has
not learned **when** to switch from breaking to collecting. The pickup
controller remains RGB-based, a temporary historical artifact; the
long-term user goal is a memory-derived, player-perceivable observation.
Next build/validate a **bounded visible dropped-item sensor**, not an
entity/world map, and use a new from-scratch agent with the same memory
inputs during training and frozen play. Include independent pre-aimed,
near, and truly natural-noise world tests and simple baselines. Do not
claim a general first-log skill until the agent itself discovers,
approaches, aims, mines and actually picks up wood without scripted phase
switches or privileged target labels.

| Input sensor flags | Tag | Warm 300-tick time | Feedback records | Missing frames |

Unlike the earlier pair, these use the SAME mod build, fixed 320x180

important correctness properties are **fresh on-action mining feedback**,
no leaked/cached prior stage and exact train/frozen feature compatibility.
Do NOT compare a cold 1.2-1.4s first repeat with warmed simulation rates.

## Beyond this integration audit

The completed controlled tests are encouraging evidence for modular
learning, but the **worst currently unsolved task is unstructured
resource discovery and autonomous phase selection**. The scripted handoff
and formerly RGB-based pickup do not satisfy the user's goal of a wholly
Minecraft-memory-derived, from-scratch agent. A legitimate next sensor
would report only *player-visible, nearby, first-hit/occlusion-checked
item entities* (including dropped physical wood), never the entire
world's entities, hidden loot, unseen terrain, seed or spawn oracle.
That observation should be available identically in training and scored
play, with a new versioned checkpoint that cannot be confused with the
attack-only model. Scoring must still require real inventory and freshly
tracked actual vanilla mined/picked-up events.
